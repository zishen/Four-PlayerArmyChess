# 软件生命周期与交付流程

## 1. 目的与适用范围

本流程适用于 FourJun 的需求、设计、开发、验证、发布和维护。当前项目没有 Git 仓库和持续集成配置，因此评审记录、版本控制和自动门禁属于待建设能力；在建设前，以本文档中的本地门禁作为最低要求。

## 2. 角色

| 角色 | 职责 |
| --- | --- |
| 产品/需求负责人 | 维护需求范围、优先级、规则解释和验收标准 |
| 开发负责人 | 维护架构、实现、代码评审和技术风险 |
| 测试负责人 | 维护测试计划、追踪矩阵、执行记录和缺陷状态 |
| 发布负责人 | 核对版本、制品、依赖、回退方案和发布记录 |

同一人员可以兼任多个角色，但需求确认、代码检查和验收结论应留下独立记录。

## 3. 生命周期

| 阶段 | 输入 | 主要活动 | 输出 | 退出准则 |
| --- | --- | --- | --- | --- |
| 立项与范围 | 产品目标、规则资料 | 明确用户、MVP、约束和不做事项 | `doc/requirements.md` | 每项需求有 ID、优先级和验收标准 |
| 设计 | 已批准需求 | 划分模块、状态、数据流和外部依赖 | `ARCHITECTURE.md`、必要的设计决策 | 需求有实现归属，风险已记录 |
| 实现 | 需求与设计基线 | 小步编码、格式化、单元测试、评审 | 源码和测试 | `gofmt`、测试、静态检查通过 |
| 验证 | 可构建版本 | 执行自动测试和人工验收，记录缺陷 | `doc/test-and-traceability.md` | 阻塞缺陷关闭，需求可追踪 |
| 发布 | 已验证候选版本 | 构建、制品核对、冒烟、记录版本 | 可执行文件、发布记录 | 发布清单全部通过，可回退 |
| 维护 | 用户反馈、缺陷、变更 | 分诊、修复、回归、文档同步 | `doc/issues.md`、新基线 | 问题有结论，变更重新通过门禁 |

## 4. 变更控制

1. 新需求或规则变更先分配需求 ID，并标记对既有需求的替代关系。
2. 评估对 `game`、`gui`、资源、测试和发布方式的影响。
3. 规则资料冲突时，由需求负责人给出书面决策；测试不能自行决定产品规则。
4. 实现与文档在同一变更中更新，追踪矩阵必须能指向测试或人工验收项。
5. 影响棋盘拓扑、战斗、胜负或信息隔离的变更必须执行全部领域测试。

## 5. 开发门禁

提交候选变更前至少执行：

```powershell
gofmt -w .
go test ./...
go vet ./...
go build -ldflags="-H windowsgui" -o Four-PlayerArmyChess.exe .
```

`gofmt -w .` 会修改源码，执行前应确认工作区变更范围。发布前还需按照 `doc/release.md` 完成人工冒烟。

## 6. 完成定义

一项需求只有同时满足以下条件才可标记完成：

- 验收标准明确且已通过。
- 实现、自动测试或人工测试记录可追踪到需求 ID。
- 相关架构、用户说明和发布说明已同步。
- 没有未处置的 P0/P1 缺陷。
- 构建制品在受支持 Windows 环境完成冒烟。

## 7. 当前流程缺口

- 尚未初始化版本库，无法执行分支、评审、标签和可追溯提交策略。
- 尚无 CI、制品归档、校验和、安装包或自动发布。
- 产品规则参考之间存在冲突，当前以代码和测试描述“实现事实”，不代表规则已获业务确认。
- 测试集中在 `game` 包，GUI 和发布制品主要依赖人工验证。
